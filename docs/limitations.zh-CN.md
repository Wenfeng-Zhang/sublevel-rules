# 已知边界（有意不做的能力）

[English](limitations.md) | **简体中文**

`sublevel-rules` 的目标是**把"版本目录往下有哪些资源"这类结构描述清楚**，
不是做一门图灵完备的规则语言。下面这些是**明确不做**的 —— 写在这里，
是为了让大家不必反复试探，也为了让规则语义保持在"一眼能看懂"的复杂度上。

判断标准很简单：**每加一个语义，`_walk` 里的组合状态就多一维**，
测试要覆盖的组合数是乘法增长的。用得上的扩展值得加，
"以后可能会用"的扩展只会变成以后删不掉的负担。

---

## 1. 递归中间层（`**`）

**想要的效果**：不关心深度，直接匹配 `cache/**/abc.abc`。

**为什么不做**：

* pipeline 里目录深度基本都是固定的，真正需要"任意深度"的场景很少；
* 一旦允许递归，就要处理**软链接环**、超深目录、以及 NFS 上不可控的遍历量；
* `Rule` 现在是线性链，深度在规则里是**看得见**的，这对排查问题很值钱
  （`--describe` 一眼就知道会走到第几层）。

**现在怎么做**：按实际深度写出来；如果确实有"深度不定"的目录，用
`Level(..., collect=Action(...))` 在每一层顺手收集，或者调用方自己遍历。

---

## 2. UI 逻辑分组（非目录分组）

**想要的效果**：同一个目录下的文件，在界面上按"贴图 / 几何 / 缓存"分组显示。

**为什么不做**：纯 UI 需求，且不同 DCC、不同项目组的诉求差别很大，
现在做等于替使用方猜界面。规则只管"有哪些资源、怎么导入"，
展示层怎么组织应该由展示层决定。

**现在怎么做**：`build_operations()` 返回的条目里带了 `method` /
`type` / `relative_path` 等字段，UI 侧可以按任意维度自己分组；
也可以给 `Action` 挂自定义 option（例如 `ui_group='贴图'`），
它会随结果一起返回（`Match.options`），UI 直接读就行。

---

## 3. `Action` 级的排除名单

**想要的效果**：`Action('*.exr', exclude='*_tmp*.exr')`。

**为什么不做**：`Resolver(exclude_patterns=...)` 已经覆盖了绝大多数场景
（跳掉 `.git`、`__pycache__`、备份文件），而"只对某一个 Action 生效的排除"
可以用**更精确的正向模式**表达，语义更清楚：

```python
Action(['*_beauty.exr', '*_diffuse.exr'], method='texture')   # 比列黑名单清晰
```

**现在怎么做**：要么写正向模式，要么用全局 `exclude_patterns`。

---

## 4. 序列帧最小帧数（`min_frames`）

**想要的效果**：只有 ≥2 帧才当序列，单帧文件当普通文件。

**为什么不做**：**单帧序列就是序列** —— 新出的镜头、只渲了一帧的测试，
本身就应该是序列（`abc.%04d.exr` + `frames=[1001]`），
强行把它降级成普通文件反而会误导下游（它会丢掉"这是序列的一部分"这个信息）。

**现在怎么做**：需要区分时用 `Match.frames` 的长度判断：

```python
for match in matches:
    if match.is_sequence and len(match.frames) < 2:
        ...    # 单帧序列，按你们的下游约定处理
```

---

## 5. 需要函数 / 条件表达式的规则

**想要的效果**：在规则里写 `if`、正则、自定义比较。

**为什么不做**：规则一旦能写逻辑，就退化成"用 YAML 写 Python"，
既没有 Python 的补全和调试，也失去了"规则是数据"的全部好处。

**现在怎么做**：

* 规则里已经**没有任何**需要函数的地方 —— 全是字符串 / 布尔 / 数字，
  所以 `rule_from_dict()` 能无损地在 dict ⇄ 规则对象之间转换；
* 真需要自定义匹配逻辑时，走**命名扩展点**而不是塞表达式：
  在 Python 侧实现并在 `Resolver` 外面包一层（例如先按规则解析，
  再对结果做一次业务过滤），比把逻辑塞进配置更好维护。

---

## 6. 帧号识别刻意保持简单

帧号就是文件名里**最后一组连续数字**（`paths.split_frame()`），没有额外限制：
`mdl_v001.ma` 会得到 `frame = 1`，`abc.1.exr` 这种一位数字也会得到 `1`。
只有声明了 `Action(is_sequence=True)` 时才看得出来 —— 这类文件会被折叠成
`mdl_v%03d.ma`。

**为什么这么定**：更严格的规则（例如"至少两位数字、前面不能是 `v` / `V`"）会让本来
合法的序列**静默地不再折叠**。而序列开关本来就是显式的 —— `is_sequence=True`
要逐个 `Action` 声明，不声明就不会折叠。

**现在怎么做**：对"每个版本一个"的工程文件不要开 `is_sequence=True`。真需要更严格的
帧号规则时，针对 `split_frame()` 做一次定点修改并补测试。

---

## 7. `require_content` 只向下探测一层

`Level(..., require_content=True)` 只往候选目录里看**一层**：这足以剔除"完全是空的"
候选，又不至于为了探测去遍历整棵子树（列目录有缓存，重复探测不额外打 IO）。
如果下一层确实匹配到了东西，即使再下面一层是空的，这个候选也会被接受 ——
那条分支只是产不出结果。

**为什么保留现状**：探得更深就等于遍历规则可能永远不会访问的子树，
而这正是这个开关想要避免的开销。

**现在怎么做**：需要看两层时，把 `require_content=True` 也声明在下一层上；
或者配一个 `optional` 层 + 兜底分支，让走到死路时仍有东西可用。

---

## 8. 大小写混合时的条目顺序

`list_entries()` 按 `entry.name` 排序，用的是**大小写敏感的字符串比较**，而名称匹配
默认不区分大小写。同一个目录里同时有 `B.ma` 与 `a.ma` 时，顺序就是 ASCII 顺序
（`B.ma` 在前），不一定符合直觉。

**为什么这么定**：只有"同一目录内混合大小写"才会碰到；`mode='latest'` 走自然数字序
不受影响；换成别的口径只是换一种意外。

**现在怎么做**：顺序重要时把它写明确 —— 用 `mode='latest'`、写精确模式，
或者在解析完之后自己对结果排序。
